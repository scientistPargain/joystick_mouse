# BLE HID Joystick Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (plan executes inline in this session; subagent-driven execution is unavailable — no credits). Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the ESP32 joystick into a real BLE HID Bluetooth mouse that Windows pairs as "Bluetooth mouse", works exactly like the USB build, and lets the same dashboard tune it over USB or Bluetooth.

**Architecture:** The firmware gains a BLE HID (mouse) service, a battery service (`0x180F`) fed from an ADC voltage divider on GPIO36, and a custom telemetry service (`0x2000`) that emits the same `rawX,rawY,button\n` wire format as USB. Classic SPP is removed from the firmware. The Python app keeps the exact dashboard and config behaviour, and the transport layer gains a BLE candidate after the USB candidates.

**Tech Stack:** PlatformIO/Arduino-ESP32 (`esp32dev`), bundled `BLE` library (BlueDroid, `CLASSIC_BT_ENABLED=y`, `NIMBLE_ENABLED` not set), existing PC app (pyserial + Flask-SocketIO), `bleak` for BLE client on the PC side.

**Spec:** `docs/superpowers/specs/2026-11-14-ble-hid-design.md`

## Global Constraints

- Board: classic `esp32dev` (ESP32), PlatformIO `espressif32`, Arduino framework.
- `CONFIG_BLUEDROID_ENABLED=y`; `CONFIG_NIMBLE_ENABLED` **not set**; bundled `BLE` library is what we use.
- Flash budget: current build is ~84 % of 1.3 MB. `BluetoothSerial` and the classic BT stack must be removed from `src/` (do not touch `libraries/`), and every task that grows the firmware must confirm `pio run -e esp32dev` exits with `SUCCESS` and flash usage drops or stays within budget.
- Wire format is unchanged: `rawX,rawY,button\n` out; `BEEP:<n>\n` in. Both USB and BLE carry identical bytes.
- Input pipeline defaults: Axis-swap X↔Y (Y = horizontal), deadzone 155, ramp 0.015→(per-second 1.65), max mult 4.0, ramp time 2.9 s, sniper 0.2, tap ≤ 0.25 s, hold ≥ 0.8 s, profile cycling. Port them verbatim from the Python code.
- Auto-accept pairing (Just Works). No bonding. No BLE keyboard/consumer control in this branch.
- Battery ADC divider: GPIO36 → 100 kΩ → Li-ion positive, 100 kΩ → GND. 3.0 V → 0 %, 4.2 V → 100 %.
- `test/test_rx_framing.py`, `test/test_transport.py`, `test/test_speed_model.py` must keep passing after every task that touches the Python side.
- A `BLE` bonded/paired state must survive unpair/re-pair (Just Works).
- USB must remain the preferred transport ("cable wins").

## Review Focus

Five failure modes the spec implies that no unit test exercises directly; tests pin them to tasks:

1. **Flash exhaustion** — build exceeds flash or requires partition-table changes. Every firmware task ends with `pio run -e esp32dev` verified `SUCCESS` and flash % printed; the plan itself removes SPP to buy headroom. Task 1.
2. **Bluetooth pairing state confusion** — an already-paired Windows device may hold stale bonding info; a working build fails to connect after re-flash. Task 1's manual checklist includes an unpair/re-pair loop after every flash.
3. **A BLE client connecting but never receiving telemetry** (custom service advertising/report map subtle errors). Task 4's checklist includes scanning the custom service with a BLE scanner and confirming raw ADC notifications & a `BEEP` write.
4. **The battery divider reading the USB 3.3 V rail** (wrong wiring/wrong channel, always reading full or 0 %). Task 4's checklist mandates disconnecting USB and validating the reported level drops as a function of an actual battery.
5. **BLE + USB simultaneous operation** — the device must do both (BLE HID always, USB telemetry concurrently). Task 5's checklist flashes with both connected and confirms both paths work at once.

### Task 1: BLE HID mouse firmware — pairing, movement, buttons, wheel, battery placeholder

**Files:**
- Modify: `src/main.cpp`

**Interfaces:**
- Consumes: the bundled `BLE` library (`BLEDevice.h`, `BLEHIDDevice.h`, `HIDTypes.h`).
- Produces: `class JoystickMouse` — an object owning the `BLEHIDDevice` instance, advertised as `"JoystickMouse"`, with `mouseReport(report_id=1)` emitting mouse buttons/X/Y/wheel. Reads X/Y pins (34/35) and emits relative movement while paired. Sets battery to 100 % (constant) via `setBatteryLevel`.
- Buttons: left = button bitmask 0x01, right = 0x02 on BLE. Wheel (HID axis) reports on the wheel axis.

- [ ] **Step 1: Remove SPP from the firmware**

Delete `#include <BluetoothSerial.h>`, `BluetoothSerial SerialBT;`, the SPP begin call and the `if (SerialBT.hasClient()) …` write path. Replace `BT_DEVICE_NAME` with `JoystickMouse`. Keep USB `Serial` untouched. Verify `pio run -e esp32dev` shows a smaller flash usage than the current 84 %.

- [ ] **Step 2: Build and verify Bluetooth stays free of linker errors**

Run: `pio run -e esp32dev` → `[SUCCESS]`. Note the new flash % — this is the headroom budget.

- [ ] **Step 3: Write the mouse HID report map**

In `setup()`, construct `BLEHIDDevice` with a report map containing **one** mouse report (id 1): buttons byte (left=0x01, right=0x02), signed X and Y bytes (relative, ±127 max per report), signed wheel byte. No keyboard report in this branch.

- [ ] **Step 4: Advertisement and connection handling**

Start advertising with the HID service UUID in the adv payload, device name `JoystickMouse`, `startServices()` mirroring the ESP32 BLE example. Register a connect callback that tracks `connected = true/false` and stops/starts advertising accordingly (BLE peripheral auto-readvertise behavior).

- [ ] **Step 5: Emit a move report from the joystick**

In the `loop()`, compute relative X/Y deltas from the raw ADC deltas (apply a simple scaling constant so a pushed stick moves the cursor, sign consistent with `dy>0` → right, `dx>0` → down — X/Y axes are swapped by the module's physical orientation). Send HID input report (id 1) with the moved deltas and any pressed buttons.

- [ ] **Step 6: Map button 32 (`INPUT_PULLUP`) to left/right click**

Hold button for left click (report button 0x01) and right click via a second gesture (e.g. button + up/down deflection threshold — or simply: tap = left click this task). Wheel axis reports when `dy`/`dx` exceeds its own threshold.

- [ ] **Step 7: Flash and confirm Windows pairs the device as a mouse**

`pio run -e esp32dev -t upload`. In Windows → Add device → Bluetooth, pair `JoystickMouse`. Expected: device appears as **Mouse**, Bluetooth settings show HID service, and moving the stick moves the system cursor.

- [ ] **Step 8: Commit**

```bash
git add src/main.cpp
git commit -m "feat(firmware): BLE HID mouse — pairing, mouse movement, click, wheel"
```

### Task 2: Port the full input pipeline to firmware (deadzone, ramp, sniper, profiles, button state machine, beeps)

**Files:**
- Modify: `src/main.cpp`

**Interfaces:**

- Produces: the exact input semantics of the Python build, moved into C++, verified from a remote BLE scanner and from USB telemetry. Defaults identical to `config.json`: deadzone 155, base 0.015 px/frame→(per-second 1.65), ramp 2.9 s to ×4.0, sniper ×0.2, tap ≤ 0.25 s, hold ≥ 0.8 s for profile cycle, axis swap as in Python (`move_x = dy`, `move_y = dx`).
- USB telemetry (`rawX,rawY,button\n` over Serial) unchanged — later every value read by the dashboard still comes from the same pins.

- [ ] **Step 1: Port the math verbatim**

Implement: axis swap, deadzone check against configured `DEADZONE`, acceleration factor from hold time, sniper factor, `dt` clamped to 0.05 s, stick-held detection to reset ramp, SNIPER button state machine and mode index (mouse/scroll/media/arrow flushed into a switch once implemented). Defaults defined as `constexpr` values mirroring `config.json` (deadzone 155, base_speed 0.015→converted to px/s constant 1.65, ramp_time 2.9f, max_speed_mult 4.0f, sniper_mult 0.2f, tap_threshold 0.25f, mode_hold_threshold 0.8f).

- [ ] **Step 2: Wire the full button/gesture state machine**

`pio run -e esp32dev -t upload`; Python app in one terminal; confirm the dashboard still shows telemetry and the cursor moves with the same deadzone/ramp feel as before.

- [ ] **Step 5: After confirming USB, confirm BLE movement feels the same**

Disconnect USB tooling; Windows system cursor follows the stick with the same ramp/deadzone, sniper engages on a held button, and profile beeps confirm.

### Task 3: Battery service (0x180F) with ADC reading from GPIO36

**Files:**
- Modify: `src/main.cpp`

**Interfaces:**
- Consumes: `BLEHIDDevice::setBatteryLevel(uint8_t)` from Task 1's device object.
- Produces: battery level reported every 5 s as `0..100 %`, computed from battery voltage read on `GPIO36` with a 100 kΩ/100 kΩ divider (measured ADC `0..4095` mapped to `3.0..4.2 V` linear → `0..100 %`).

- [ ] **Step 1: Add ADC divider constants and a read function**

`BATTERY_ADC = GPIO_NUM_36`, `BATTERY_ADC_CHANNEL = ADC1_CHANNEL_0`, `ADC_TO_VOLTS(x) = x * (2.1 / 4095.0) * 2.0` (two 100 kΩ legs, so effective input is half the battery voltage). Add `readBatteryPercent(): uint8_t` with clamps: `V < 3.0 → 0`, `V > 4.2 → 100`.

- [ ] **Step 2: Update the battery level every 5 s**

Stash the timestamp; every 5 s compute the level and call `setBatteryLevel()`.

- [ ] **Step 3: Flash, unplug USB, and confirm the reading stabilises**

Expected: a number other than 100 % (the constant placeholder), plus a change in the reported level when the pack is loaded (e.g. by briefly touching a load across the divider or comparing full/empty phases).

### Task 4: BLE telemetry + control service (`0x2000`) — same wire format as USB

**Files:**
- Modify: `src/main.cpp`

**Interfaces:**
- Consumes: Task 2's battery baseline call and Task 1's device object.
- Produces: a custom 128-bit service UUID `00002a02-0000-1000-8000-00805f9b34fb` with two characteristics:
  - `00002a02-0000-1000-8000-00805f9b34fb` — notify, identical bytes `rawX,rawY,button\n`.
  - `00002a03-0000-1000-8000-00805f9b34fb` — write, accepts `BEEP:n\n`.
  - The service advertises the same payload for discovery. Connection is unchanged.

- [ ] **Step 1: Create the custom service with the two characteristics**

Use `BLEServer::createService()` with a custom `BLEUUID`. Add a `notify` characteristic (for telemetry) and a `write` characteristic (for BEEP). Start notifications on connect and stop on disconnect.

- [ ] **Step 2: Send telemetry over BLE whenever connected**

In the loop, alongside USB writes, push the identical frame to the notify characteristic. Keep USB active regardless — the firmware must serve both links simultaneously.

- [ ] **Step 3: Accept `BEEP:n` on the write characteristic**

An `onWrite` handler parses the incoming bytes for `BEEP:<n>` and drives the buzzer (pin 25) with the same timing as the current firmware (80 ms on/off, `n` times).

- [ ] **Step 4: USB and BLE together — flash and verify both work at once**

USB reader running, Windows cursor moving via BLE, de-attach USB → dashboard disconnects but cursor still moves via BLE; re-attach USB → both paths alive simultaneously.

- [ ] **Step 5: Confirm the service from any BLE scanner**

Windows: run `btget-info`/wireshark-ble or any BLE scanner (e.g. "nRF Connect"), open the custom service, confirm notifications stream raw tuples and writing `BEEP:3` buzzes three times.

- [ ] **Step 6: Commit**

```bash
git add src/main.cpp
git commit -m "feat(firmware): BLE telemetry + BEEP control service (matches USB wire format)"
```

### Task 5: PC app — BLE candidate in the transport layer and dashboard badge

**Files:**
- Modify: `pc_side_py/transport.py`
- Modify: `pc_side_py/app.py`
- Modify: `pc_side_py/templates/index.html`

**Interfaces:**
- Consumes: `BLE` services from Task 4 (found by scanning for the HID service UUID or the custom service UUID).
- Produces: `discover_ble()` (in `transport.py`) that rturns `(name, kind="bluetooth")` when the device advertises; `connect_ble(address)` returning a `BleJoystick` object exposing the same `in_waiting`/`read` semantics? No — `BleJoystick` exposes `.read_frame()`/`.send_beep(n)` via `bleak`; the app's background loop treats it identically to a serial port for this path.

- [ ] **Step 1: Add `bleak` and a BLE path to the transport layer**

`pip install bleak` (done already). New module-level constants: service UUID `00002a02-...`, write characteristic UUID `00002a03-...`.
New function: `discover_ble(timeout=1.5, scan=None)` → returns `BLEDevice | None` using `bleak.BleakScanner.discover(timeout=timeout)`; classify any device advertising the custom service UUID as our joystick. USB probing stays.

- [ ] **Step 2: Make the transport layer treat BLE as a candidate**

`discover_link` gains the BLE path: first USB (unchanged, wins if streaming), then BLE. On connection, `BLEClient` runs `start_notify` for the telemetry characteristic and queues frames; the app's `update()` loop reads the same bytes the USB reader produces. `Link` gains `kind="bluetooth"` — the dashboard badge shows `Bluetooth (JoystickMouse)`.

- [ ] **Step 3: `app.py` — accept either transport**

`joystick_controller = JoystickController(link.serial)` is USB-only. Refactor minimally: `JoystickController` accepts any object with `in_waiting`/`read`/`write`. Provide `BleSerial` shim that wraps the BLE notify queue with `in_waiting` and `read`, and `write(bytes)` via the write characteristic. The dashboard emits `link_status` unchanged.

- [ ] **Step 4: Dashboard badge + README/AGENTS updates**

Small UI change (badge label only). Add a "Wireless" section to README and update AGENTS.md quirks accordingly.

- [ ] **Step 5: Validate (USB first)**

`cd pc_side_py; .\venv\Scripts\python.exe app.py` with USB connected — unchanged behaviour, badge `USB (COM10)`, telemetry live.

- [ ] **Step 6: Validate BLE**

Unplug USB, restart the app. Expected: dashboard shows `Bluetooth (JoystickMouse)`, live telemetry flows, beeps trigger.
